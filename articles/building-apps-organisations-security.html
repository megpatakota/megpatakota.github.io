Building Apps Inside Organisations: The Security Work Beyond the Demo

A practical guide to the decisions between a working app and a responsible rollout: permissions, data boundaries, AI actions, evidence and ownership.

In this article

An AI demo can answer a question. A shared research assistant must answer using the right evidence, for the right person, with controlled access and actions.

Our example: an internal assistant that searches approved project documents, answers with citations and drafts research briefs. Start with one team, selected sources and read-only retrieval. This is an illustrative design.

1. Protect the evidence before generating an answer

A login establishes identity. The backend still needs to enforce project and document permissions before retrieved passages reach the model.28

Restricted content appears

Control
Filter documents before model access; never accept a user-selected access scope.
Verify
Try search, direct document links and exports as users with different permissions.

Revoked access lingers

Control
Set a revocation window, synchronise permissions and invalidate affected caches.
Verify
Remove access, then repeat retrieval, citation and saved-brief requests.

A citation misleads

Control
Link claims to accessible passages; make missing or conflicting evidence visible.
Verify
Use known-answer questions and questions the collection cannot answer.

Check the connector’s identity as well: a maker-owned connection can grant more reach than the researcher has.3

2. Follow the copies, not just the database

Source documents→Search / embedding index→Model context→Answers and briefs
Also check: conversation history, caches, exports, backups and monitoring logs.

For each location, record who can access it, which service receives it, retention and deletion. Keep logs focused on the actor, operation, outcome and trace reference; decide deliberately whether document content belongs there.4

3. A document is evidence, not an instruction

A retrieved document might tell the assistant to search a restricted collection or share a brief externally. Prompt-injection filters help, but permissions and allowed actions must be enforced outside the model.56

Expose narrow tools for approved search, authorised passages and draft saving. Restrict destinations and network access. Test an injected document through the real workflow, checking tool calls and side effects as well as the answer.10

4. Choose tools by the gap they address

Use existing organisational tooling first. Code review, dependency checks, web testing and AI attack testing cover different layers.

Code review

Claude Security · Semgrep · Snyk Code

Investigate source-level flaws; review proposed fixes and add regression tests.11121416

Check beta access, language coverage and code-processing terms. Semgrep CE can scan locally.15

Dependencies

Snyk Open Source

Find vulnerable direct and transitive packages and licence issues.17

Triage reachability and upgrade risk. This does not verify document permissions.

Web application

ZAP

Check staging responses, cookies and headers; configure authentication for protected routes.18

Baseline scanning is passive. Business access rules need their own tests.

AI attack testing

Promptfoo · Mindgard

Exercise indirect injection, cross-user access and tool abuse.192021

Test the full retrieval/tool path and inspect effects, not just model refusals.

Runtime and cloud exposure

Model Armor · Wiz

Evaluate content screening or code-to-cloud exposure, depending on the product.2324

Verify purchased coverage, blocking behaviour and reproducible findings.

Low-code governance

Copilot Studio data policies

Allow, group or block connectors in the intended environment.22

Connector policies do not replace document-level authorisation.

Claude Security: which product are we talking about?

The February research preview was named Claude Code Security. Current documentation describes Claude Security, an Enterprise public beta and a Claude Code plugin.291112

The separate security-review GitHub Action is intended for trusted pull requests; its repository says it is not hardened against prompt injection. Check workflow permissions before enabling it.13

5. Turn each concern into evidence

Concern→Control→Owner→Test→Evidence
Different usersNo cross-project search, citation or export leakage.
Revoked accessIndex, cache and saved-brief checks meet the revocation window.
Injected documentNo unauthorised retrieval, tool call or external share.
Changed approvalEdited, expired and replayed approvals fail; retries do not duplicate sharing.
Missing evidenceThe answer acknowledges gaps; citations support its claims.
Protection outageRequired permission checks fail closed; guardrails follow the chosen failure policy.

Run relevant code/dependency checks and access tests in CI; add authenticated web and AI attack tests in staging. Record versions, confirmed findings, fixes and any time-limited exceptions.

Which frameworks help choose the checks?

OWASP ASVS: application requirements. OWASP LLM and Agentic Top 10: model and tool risks. MITRE ATLAS: adversary scenarios. NIST SSDF: development practices and evidence. Framework mapping is not certification.7525261

6. What organisations report doing

Microsoft

Its internal MCP account describes vetted servers, scoped identities, gateway controls and consent checks; some end-to-end logging remains work in progress.10

Docker

OpenFGA’s case study describes comparing old and new permission decisions before incrementally switching traffic.27

Snowflake / DoorDash

Anthropic publishes customer accounts of Claude Security testing and engineering-workflow integration.28

These are organisational accounts and vendor-published case studies, not an independent ranking. Compare tools on the same seeded failures, false positives, fix effort, data exposure and integration cost.

7. Start small. Revisit when the reach changes.

First release

One team. Selected sources. Read-only retrieval. Cited answers. Reviewed drafts.

Review triggers

New collections, model, connector, shared memory, external audience or write capability.

Ownership and obligations

Name support and shutdown owners. Check applicable privacy, contract and retention decisions; technical tests alone do not resolve them.

Keep a route to disable tools, roll back changes and retire the assistant. The release decision should explain who may use this version, with which data and actions—and point to the evidence.
