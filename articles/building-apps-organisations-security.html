Building Apps Inside Organisations: The Security Work Beyond the Demo

A practical guide to the decisions between a working app and a responsible rollout: permissions, data boundaries, AI actions, evidence and ownership.

In this article

There is a satisfying moment when an app starts working.

The form submits. The dashboard updates. The assistant finds the right document. Someone tries it and says, “We could actually use this.”

With AI coding tools, low-code platforms and configurable agents, that moment can arrive quite quickly. The harder conversation starts when someone wants to share the link with a team, connect a real system, or use the output in client work.

Who can see what? Whose account is the app using? Where does the data go? What happens if the answer is wrong? And who is responsible for the thing six months from now?

That is the part of building apps inside organisations I think deserves more attention. A useful prototype gives people something to react to. A dependable tool needs decisions that hold up beyond the demo.

My starting point

Security should help a team understand the conditions under which its app can be used: by whom, with which data, to do what, and with what evidence. That conversation can begin while the idea is still small.

Start With the Work the App Will Actually Do

Imagine an internal briefing app. It searches approved project documents, reads a few CRM fields and drafts a summary before a meeting. A person checks the draft before using it. This is an illustrative example, rather than a report of a particular deployment.

It sounds straightforward. But “an internal AI app” is too broad a description to make useful security decisions.

I would want a short brief: the intended users, the documents and records in scope, the output, the actions it can take, and the things it must never do. For this first version, perhaps that means one project team, selected source folders, read-only CRM access and no external sending.

The amount of review should follow the consequences. A prototype using synthetic data has a different exposure from a shared app containing client material. An app that drafts a note has a different failure mode from one that approves a payment. “It is only internal” does not explain either distinction.

NIST’s Secure Software Development Framework places secure development practices within the development lifecycle. I read that as a useful reason to make these questions part of delivery, rather than leave the whole conversation until the final release meeting.1

A Login Does Not Explain What Someone Can Access

Signing in establishes an identity. It does not, on its own, establish which project records that person should be able to retrieve, summarise, download or change.

For the briefing app, the important question is whether the app preserves the boundaries between projects. If Priya can open Project A but not Project B in the source system, can she still obtain a Project B summary through the app?

Hiding a button or filtering a list in the browser is insufficient. The service handling a request needs to enforce the relevant permissions. OWASP’s authorisation guidance recommends least privilege, denying access by default and validating permissions on every request.2

There is another identity to follow: the connection to the underlying system. An app might authenticate the employee, then make a CRM request through a much more privileged account. The reassuring sign-in screen has not resolved that boundary.

Microsoft documents this distinction in Copilot Studio. A tool can use its maker’s credentials or the end user’s credentials; maker-provided connections can expose data or capabilities beyond the end user’s permissions. Check the particular connector, channel and runtime configuration rather than assume every agent behaves the same way.3

A test worth running

Create two test users with different project access. Try normal search, direct record requests, downloads and generated summaries. Check that restricted material is excluded from both the retrieved context and the response. Keep the test cases and results; a successful demonstration using an administrator’s account tells a much smaller story.

How I would preserve project permissions in a retrieval app

First, validate the session or access token on the backend and derive the user and organisation from that verified identity. Do not trust a user ID or tenant ID supplied in the request body. Then check access to the requested project and apply document permissions before any text reaches the model. Downloads, citations and exports need the same boundary.

For a small app, those checks may live in the existing service and database. If permissions span groups, projects and documents, a relationship-based authorisation service such as OpenFGA can answer whether a user may read a particular object. It still needs an accurate permission model and an application that enforces its decisions.8

# Pseudocode: each helper represents a backend control.
# Invalid identity or unavailable policy checks stop the request.
actor = verify_session(request)
project = load_project(request.project_id, actor.organisation)
require_permission(actor, "read", project)

chunks = search_with_permission_filter(
    query=request.query,
    organisation=actor.organisation,
    project=project.id,
    permissions=current_permissions(actor)
)
require_permission_for_each(actor, "read", chunks)
return generate_summary(context=chunks)

The search filter must be constructed by the server, and each chunk must inherit its source document’s permissions. Azure AI Search documents both security-trimming patterns and native document-permission features; several native integrations remain in preview. Source permission changes only affect indexed results after the relevant metadata synchronises. That delay is part of the design, not an implementation detail to discover after launch.9

I would explicitly test removing someone from a project: can they still retrieve an old chunk, follow a citation, open a saved summary or receive a cached answer? Define the acceptable revocation delay, invalidate permission-sensitive caches, and use a fresh source check or suspend retrieval when stale metadata would be unacceptable. Passing one search test does not establish that every derived copy is protected.

The Data Boundary Extends Beyond the Main Database

A diagram that stops at “app → database” can miss where information actually travels.

The briefing app might send a document extract to a model service, keep a search index, store a draft, record a conversation and send an error event to a monitoring tool. Each creates another place to think about access, purpose, retention and deletion.

I would draw that path, including the less visible copies: caches, exports, derived summaries and backups. Then ask which service receives each part, what is necessary for the task, and how long the information needs to remain there.

Logs deserve their own conversation. They are useful for investigating problems, but can become an unintended store of prompts, document extracts or identifiers. OWASP’s logging guidance describes information that should generally be excluded, masked or otherwise handled carefully, including access tokens, passwords and sensitive personal data.4

For our example, a useful event might record the action, an authorised actor identifier, time, outcome and a trace reference. Whether any content belongs in the log needs a deliberate decision. “Log everything so we can debug it later” is a poor default for client material.

The same care applies to vendor statements. Establish the exact service, plan, region, settings and terms being used. A statement about one product is not a substitute for checking the configuration through which your app actually processes data.

AI Adds Another Boundary: What It Reads Versus What It May Do

Now imagine a source document containing an instruction to send the briefing somewhere else. The document is material the app should analyse. It is not an authorised request to change the workflow.

That is why prompt injection matters beyond unusual chatbot answers. Instructions can arrive inside retrieved documents and other external content. OWASP notes that retrieval-augmented generation and fine-tuning do not fully mitigate this risk.5

I would keep authorisation and the permitted action set outside the model’s discretion. The model can propose a summary or an action. The surrounding application still checks the identity, project, destination and permitted operation. A sentence in the system prompt is not an access-control mechanism.

The distinction becomes sharper if the briefing app gains an email tool. Drafting and sending need different controls. Start with the narrow capability the work requires, and add a specific approval step where the consequence warrants it. OWASP’s excessive-agency guidance connects this risk to excessive functionality, permissions and autonomy.6

“Human in the loop” needs a usable interface too. The reviewer should see the proposed recipients, the actual content, relevant sources and the action they are authorising. If those details change, the earlier approval should not quietly authorise a different send.

Turn a proposed action into a controlled operation

For the briefing app, I would expose narrow tools such as read_project_record and create_draft, rather than an unrestricted HTTP client or shell. The backend validates the argument schema, checks the user’s permission for the target object and restricts destinations. A model-supplied URL must not let the tool reach internal metadata services or an unapproved external host.

If sending is later introduced, store the proposed recipients, content and attachments as an immutable server-side draft version. Bind approval to that version, the approving user, the permitted action and an expiry. At execution, recheck current permissions and consume the approval once; changed content or recipients require a new approval. Use an idempotency key and an atomic state transition so a retry does not create a second send. These are proposed implementation controls, not features automatically supplied by an agent framework.

For MCP integrations, I would also record the approved server and tool definitions, restrict its file and network reach, and require review when its capabilities change. Microsoft’s account of its internal MCP governance describes vetted servers, scoped identities, gateway enforcement and consent checks—concrete controls around the integration, beyond the protocol itself.10

Test the effect, not just the answer

Put a conflicting instruction in a synthetic source document. Check both the response and the tool trace: did the app retrieve another project, attempt an external call or send anything? A polite refusal is insufficient evidence if an unauthorised operation has already happened.

The Implementation Still Needs Ordinary Security Work

AI can help write code and identify possible issues. It cannot establish that the finished app’s access rules, deployment settings or business logic are correct.

For a custom web app, the familiar work remains: handling sessions, keeping secrets out of browser code, validating inputs, checking permissions at the service boundary, reviewing dependencies and testing failure paths. Generated code needs the same scrutiny as code written another way.

OWASP’s Application Security Verification Standard gives teams a basis for specifying and testing technical application controls. It is more useful to choose relevant requirements and verify them against the actual implementation than to write “OWASP checked” beside a release.7

A scanner is one source of evidence. It will not, by itself, explain whether the right person can export the right project, whether a revoked permission takes effect, or whether a draft is being sent to the wrong client. Those questions need tests of the workflow and its rules.

Which Tools Would I Consider, and for What?

The selection depends on what the app is made of. Source-code analysis, dependency analysis, testing a running web service and attacking an AI workflow answer different questions. A platform-built app also needs configuration and connector review, even when there is little custom code to scan.

Claude Security is relevant here. Anthropic launched the earlier Claude Code Security research preview in February 2026.29 Its current product page describes Claude Security and a separate Claude Code plugin in beta; the help centre documents the Enterprise public beta. The product scans code for vulnerabilities and proposes patches for human review. Those capabilities make it a candidate for investigating a missing access check or a data-flow flaw—not proof that deployed permissions, connector configuration or contractual requirements are correct.1112

Anthropic also maintains a separate security-review GitHub Action and documents the /security-review command. Its Action repository explicitly limits use to trusted pull requests because it is not hardened against prompt injection. A team should review its workflow permissions and contributor trust boundary before enabling it.13

Use frameworks to choose checks, then make the checks executable

For the web application, select relevant OWASP ASVS requirements and turn them into acceptance tests. For model and retrieval risks, use the OWASP LLM guidance; for tool-using agents, include the OWASP Top 10 for Agentic Applications 2026. MITRE ATLAS provides adversary techniques to help construct attack scenarios. NIST SSDF helps organise the development practices and evidence across the lifecycle. These references serve different purposes; mapping a tool to a framework is not a certification of the finished app.7525261

What Would Convince Me That a Fix Works?

For the briefing app, I would keep a small set of deterministic integration tests alongside the generated AI attack cases. Use synthetic records with recognisable markers and inspect the retrieved context, tool calls, side effects and permitted audit fields. Repeat model-dependent cases across runs and keep the model, prompt, index and policy versions with the results.

Example tests to run before broadening the pilot
Potential failureTest and expected evidence
An employee crosses a project or organisation boundary.Change the requested project, document and export IDs; try the search and direct endpoints. No restricted content reaches the model or response. The denied operation creates no side effect.
Revoked access survives in an index or cache.Remove project access, then repeat search, citation, download and cached-summary requests. Check the documented revocation window and the behaviour when permission synchronisation fails.
A source document redirects the agent.Insert a synthetic conflicting instruction through the real retrieval path. Confirm the agent cannot widen its permissions, reach an unapproved destination or execute an unapproved tool.
Approval is reused after a draft changes.Edit the recipient or content, replay an expired approval, and retry the send. Changed or expired approvals fail; an accepted retry does not duplicate the operation.
A protection service is unavailable.Simulate an authorisation timeout and a guardrail outage. Permission checks fail closed; the guardrail follows the chosen failure policy rather than silently changing behaviour.

In CI, I would run the relevant code and dependency checks plus those access tests on changes. A staging workflow can add authenticated web scans and AI attack tests. Confirmed release-blocking findings need an owner and a regression test; exceptions need a recorded reason, expiry and reviewer. An AI-generated report should not be the only evidence that an AI-generated patch worked.

What Are Organisations and Vendors Actually Doing?

There are useful public examples, but they do not show that every organisation has reached the same level of maturity.

Microsoft’s internal account is an implementation example. Microsoft Digital and its CISO organisation describe a vetted MCP server catalogue, gateway controls, scoped identities, consent checks and change review. The article also says some end-to-end logging is work in progress. That makes it a more useful reference than assuming the whole programme is already complete.10

OpenFGA’s Docker case study describes a production authorisation migration. It reports that Docker centralised permissions and ran the new engine alongside the previous one, comparing decisions before incrementally switching traffic. This is a maintainer-published customer case study, not an independent benchmark, but the migration approach is concrete.27

Anthropic reports customer use of AI-assisted vulnerability review. Its April 2026 Claude Security announcement includes Snowflake describing findings from early testing, and DoorDash describing integration into engineering workflows. Those are vendor-published customer accounts; they support evidence of use, not a comparative claim that Claude detects more vulnerabilities than every alternative.28

The platform offerings now span several layers. Copilot Studio provides connector policy controls, Google offers runtime screening, and Wiz describes connecting code findings with cloud and runtime exposure. My inference from these product documents is that buyers need to evaluate how the layers work together. Buying one “AI security” product does not establish coverage of the whole application.222324

For a pilot, I would compare candidates using the same seeded failure cases: confirmed issues found, false positives, time to reproduce and fix, integration effort, data sent to the vendor, latency where applicable, and evidence retained. The sources here do not provide a like-for-like independent benchmark, so I would not rank these products by efficacy or invent adoption percentages.

Turn the Concerns Into Work Someone Can Finish

A list of risks can leave a team feeling informed but stuck. “Sort out access”, “check the AI” and “get compliance approval” are not yet a delivery plan.

I find the more useful unit is a specific concern connected to an action, an owner, an acceptance criterion and evidence. It gives the builder something to implement and the reviewer something concrete to assess.

Illustrative plan for the briefing app
ConcernAction and ownerEvidence to review
Project boundaries are lost in search.Application team: enforce record-level access before retrieved content reaches the model.Tests using users with different access, including direct requests and permission revocation.

A draft could be sent to the wrong recipient.Product owner and application team: require approval of the exact destination and content.Tests showing blocked unauthorised sends and renewed approval after edits.

These are starting examples, not a complete assessment. The important distinction is between an action being planned, implemented and verified. A status change should point to something that was inspected or tested.

The review should also record what remains uncertain, who is accepting any residual risk, and the conditions of the release. An unresolved question is easier to handle when it has a named owner and a clear effect on scope.

Security Evidence Helps the Compliance Conversation. It Does Not Finish It.

A team can complete its technical tests and still have unanswered questions about using client information, contractual restrictions, retention commitments or the purpose for which personal data is processed.

I would bring the relevant data owner, privacy, legal or procurement colleagues into the specific decisions that need them. Show them the data flow, service details, intended users and actions. “Please approve our AI app” leaves too much hidden.

The result may be a narrower pilot, different terms, a change in processing or a decision to leave certain data out. The right answer depends on the organisation and use case. A control checklist cannot determine those obligations on its own.

Similarly, an application review should state exactly what was reviewed. It should not imply that a small app has earned an organisation-wide certification, or that completing a framework automatically establishes compliance.

The Next Connector Can Change the Original Decision

The briefing app begins with selected documents. A month later, someone asks for broader CRM access. Then automatic email sending. Later, access for an external partner.

Those are changes to the app’s reach. They can affect whose information it sees, what it can do and who carries the consequences.

I would keep review triggers alongside the plan: a new source, role, connector, model service, external audience or write capability. Each trigger should prompt the team to revisit the affected decisions and tests. It need not restart every unrelated piece of work.

Previous evidence is still useful history, but may not support the new version. Keep the earlier decision and record why something has reopened.

There is an operational side too. Name the person responsible for support, the route for reporting a problem, and who can disable a connector or stop a release. Include a way to roll back, recover and eventually retire the app. Ownership needs to survive the person who built the prototype moving to another project.

Give the Team a Route From Idea to Responsible Use

If I were starting this conversation with a team, I would put one page in front of us: what the app does, who uses it, the data path, the actions it can take, the main unanswered questions and the people who own them.

From there, choose the smallest useful release, turn the relevant concerns into testable work, and agree what evidence a reviewer needs. Make the conditions visible to the people using the app as well as the people building it.

For the briefing app, that might mean a read-only pilot with a small group, selected sources and reviewed drafts. Wider access or sending can follow when the additional controls and evidence are ready.

That gives a builder a clearer route to a useful rollout. It also gives the organisation a way to revisit the decision as the app changes.

The question I would want a team to answer is simple: can we explain why this version is appropriate for these users, this data and these actions—and show the work behind that decision?
